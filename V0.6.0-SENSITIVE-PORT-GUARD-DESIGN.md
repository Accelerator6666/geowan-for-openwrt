# GeoWAN v0.6.0 — Sensitive Port Guard Design

## Purpose

Add a separate Sensitive Port Guard to GeoWAN for monitoring and (in a later, explicitly enabled stage) blocking suspicious inbound activity against services published through WAN DNAT. It complements, but does not replace, the existing GeoIP country filter.

The feature must protect domestic sources as well as any other source that reaches an exposed service. Country classification is context only; it is not a trust decision.

## Compatibility and safety boundaries

- Keep the existing v0.5.1 GeoIP filter, `geo_black4/6` sets, DNAT redirects, firewall rules, daed/proxy routing, VPN and existing service exposure unchanged.
- Do not add a listening TCP/UDP port.
- Do not place per-router public port mappings, private IP addresses, or allowlists in this repository. Discover redirect inventory from the router's local UCI configuration and store user overrides locally.
- Do not reuse or reinterpret the existing GeoIP `events` table as complete connection telemetry. v0.5.1 only samples `GEOWAN4/6` log records from the existing GeoWAN filter; this is not a feed of all accepted domestic DNAT connections.
- Add a separate event namespace/table and separate nftables objects for Guard.
- Installation defaults to observation-only. No automatic blocking until a later stage has passed on-device validation and the operator explicitly enables enforcement.
- The installer/preflight must not reload firewall, alter redirects, alter existing rules, or change GeoIP sets. Guard-owned rules/sets must be identifiable and independently removable.

## Router-derived service inventory

Read enabled WAN `config redirect` sections from UCI. Normalize each mapping to:

- address family (IPv4/IPv6/dual/unknown)
- protocol (TCP/UDP/other; preserve the configured value)
- public/original destination port (`src_dport`)
- post-DNAT destination address (`dest_ip`)
- post-DNAT service port (`dest_port`)
- redirect name and enabled state
- last-seen configuration fingerprint

Use the conntrack original destination port for matching forwarded traffic after DNAT (for example, `ct original proto-dst`), not the translated backend port. Confirm the exact fw4 hook and chain order on the target router before installing rules.

Detect and surface ambiguous mappings. Two redirects sharing the same address family, protocol and public port but targeting different backends must be marked as a conflict; do not enforce an automatic policy for that mapping until resolved. The same port in IPv4 and IPv6 is not by itself a conflict.

## Policy model

Each discovered mapping receives a local policy profile:

1. **Management / administration** — examples include RDP, VNC, hypervisor consoles, backup consoles, NAS administration and firewall administration.
2. **Remote access / VPN** — SSLVPN and other explicitly designated remote-access endpoints.
3. **Published application** — media, collaboration, download, home automation, document and user API services.
4. **Custom / unclassified** — operator-defined or unknown service.

Classification is advisory and editable. Never infer a service solely from a port number when the redirect name or backend is ambiguous.

Per-source policy supports:
- observe only
- alert on threshold
- temporary source+public-port block
- temporary source-wide block for confirmed multi-port scanning

A trusted-source allowlist may bypass Guard actions only. It must never bypass the existing GeoWAN country block or other firewall policy.

## Detection and telemetry

Observe new inbound forwarded connections after DNAT and before the final accept decision, using the confirmed fw4 forward path. Preserve source address, address family, transport protocol, public/original destination port, translated destination address/port and timestamp.

Use a dedicated SQLite table (for example, `guard_events`) and indexes. Keep existing `events`, GeoIP analytics and correlation semantics unchanged. Record whether a row is a sampled log event or a counter-derived observation; never label rate-limited log samples as complete connection counts.

Initial v0.6.0 scope:
- UCI redirect inventory and conflict detection
- Guard event capture in observation-only mode
- per-service and per-port activity summaries
- source profile by public/original destination port
- explicit monitor/disabled state and local policy configuration
- IPv4/IPv6 visibility
- LuCI panel for inventory, activity, alerts and audit trail

## Enforcement stage (not enabled by v0.6.0)

A later release may add:
- a dynamic tuple set for source-address + public-port temporary blocks
- a separate source-wide temporary block set for multi-port scans
- bounded TTLs, escalation and automatic expiry
- manual unblock and audit reason
- explicit global enable/disable and per-service enforcement mode

Use separate Guard-owned nftables sets/chains; never add Guard offenders to `geo_black4/6`. A port-specific violation must not block the same source from unrelated published services. A source-wide block requires stronger multi-port evidence and must be separately configurable.

## Required target-router checks before firewall integration

1. Capture complete UCI redirect sections, including `proto`, `family`, `enabled`, `src_dport`, `dest_ip` and `dest_port`.
2. Resolve duplicate public mappings (notably the reported public port 35006) by checking protocol and actual nftables DNAT rules.
3. Inspect the full attributes and target of the broad WAN firewall rule reported as rule index 35; do not infer its action from its display name.
4. Inspect `geo_wan_forward`, the fw4 `forward` chain and DNAT chain order. Identify the exact safe hook after DNAT and before accept.
5. Run `fw4 check` and an nftables syntax check for Guard-owned rules without reloading firewall.
6. Validate observation-only logging with a controlled connection from an operator-owned test source. Confirm that the recorded public port is the original WAN port, including custom RDP ports and IPv6.

## Acceptance criteria

- Existing GeoWAN service, counters, bans, GeoIP cache and v0.5.1 analytics remain unchanged.
- No existing redirect, WAN rule, DNAT target, proxy setting or listening port changes.
- All enabled WAN redirects are inventoried with protocol and family.
- Duplicate/ambiguous mappings are visible and excluded from enforcement.
- A controlled connection to a custom public RDP port is attributed to that public port, not only backend TCP/3389.
- IPv4 and IPv6 are independently represented.
- Observation-only mode cannot drop or reject traffic.
- Uninstall removes only Guard-owned files, chains and sets, and leaves existing GeoWAN objects intact.
